## 2026-10-14 Windows 版の候補の窓は DLL が描く

- これまではエンジン（Java の Swing）が自分の窓に出していた。見た目を Windows 11 に合わせにくく、クリックすると入力欄からフォーカスを奪って入力中の文字が消えた（Java だけでは WS_EX_NOACTIVATE にできない）
- MS-IME と同じく、DLL がアプリのプロセスの中に Direct2D・DirectWrite で描く。角の丸め（DWM）・影・アクセントの色・カラー絵文字。エンジンは候補の一覧を命令（cands）で送るだけになり、画面を持たない
- 座標は入力欄と同じプロセスなので、拡大率に対応していないアプリでもずれない（エンジンに送っていたときは物理ピクセルに直す必要があった）
- クリック: WM_MOUSEACTIVATE で選んで MA_NOACTIVATEANDEAT を返す（クリックのメッセージを作らせない）。それでも IMM のアプリでは、システムのフックが先にクリックを見て入力中の文字を確定させる。DLL では止められないので、仕様の制限として残す
- 試してやめたこと: Compose for Desktop で候補の窓を作り直す案（本人が設定の画面を WinUI 3 に決めたのと合わせ、窓は DLL に寄せた）

## 2026-10-14 音声の途中表示を Nemotron-3.5 の逐次認識に（落としてあるとき）

- 予定にあった案B（`docs/RESEARCH-voice.md`）を作った。sherpa-onnx 1.13.8 の OnlineRecognizer で、`csukuangfj2/sherpa-onnx-nemotron-3.5-asr-streaming-0.6b-560ms-int8-2026-06-11`（約 682MB、リビジョン固定）を使う。届いた音声だけを流すので、話が長くなっても1回の計算が増えない。句読点も付く
- Nemotron は「モデル」の一覧から落とす。落としてあれば途中表示はこれ、なければ今までどおり ReazonSpeech（仮決定。戻すには一覧から Nemotron を削除する）。確定用として「適用」もできる
- 区切りは 560ms 版にした（80/160/320/1120 もある）。仮決定。速さと精度の兼ね合いは実機で見直す
- 流れの頭に 0.25 秒の無音を足す。見本の音声（いきなり話し始める）で「今日はいい天気ですね」が「キュワイ天気ですね」になり、足すと直った
- 聞き続けるモードでは、区切ったら流れを始め直す（`VoiceInput.epoch` が変わったら）
- 速さ: Pixel 3（Snapdragon 845）の4スレッドで 8.2 秒の音声に 7.6 秒（RTF 0.93）、読み込み 6.6 秒。Fold 7 は未測定。エミュレータでは入れ直した直後の読み込みが 12 秒を超え、その間は途中の文字が出なかった
- 見つけたこと（未対処）: ReazonSpeech は後ろに長い無音（31 秒）が付くと文末を落とす。押したまま長く黙ると、確定の文が欠けることがある

- **予測の候補**: 辞書の読みは辞書順に並ぶので、接頭辞の範囲を二分探索で取り、範囲の語をコスト＋（伸びた読みの文字数×400）で並べる。重み 400 は、「きーぼ」でキーボードが先、「ありがと」でありがとうが先になる程度に置いた。当てはまる読みが 3 万を超える接頭辞と1文字の読みでは引かない。実際の辞書で 0.1〜6ms。読み全体で見つからなければ最後の文節の読みで探す（「きょうはきーぼ」→ 今日はキーボード）。zenz では並べていない（打つたびに推論が増えるため）。並びがおかしい例: 「しゅうせ」の1位が「修せよ」、「てんき」の1位が「転勤」。ひらがなのままの語は、はじめ外したが「ありがと」で「ありがとう」が消えたので戻した。
