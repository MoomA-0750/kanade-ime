# Kanade の計画

2026-10-02 に CC との会話で方針を決めた。この文書がその会話の引き継ぎ資料で、会話履歴は残っていない前提で書いている。

## 目的

Samsung DeX で使う、物理キーボード最適化に全振りした Android 用日本語 IME を作る。

- 無駄なポップアップや画面キーボードなどの UI を出さない
- 変換は zenz（Zenzai）などの AI ベースで、ライブ変換を持つ
- 音声入力は Whisper などで行う
- 以上を可能な限りローカル（端末内）で動かす

## 本人が決めたこと（2026-10-02）

| 項目 | 決定 |
|---|---|
| 名前 | Kanade（リポジトリ `kanade-ime`） |
| キーボード配列 | **US 配列と JIS 配列の両方**に対応する。JIS は変換・無変換・かなキーをそのまま使う。US は日本語オン/オフを別のキー（候補: 右 Alt 単押し、Ctrl+Space、QMK で送る専用キーコード）に割り当て、設定で選べるようにする |
| 音声入力 | **押している間だけ録音（Whisper 系）と、話しながら文字が出る逐次認識の両方を切り替え**。まず押している間の録音から作り、逐次認識は後で足す |
| 進め方 | **Kite Browser と同様に完全自走**。判断は仮決定して進め、理由を記録する。GitHub への push だけは事前に確認する |
| 公開 | 当面ローカルのみ（GitHub へは上げない） |

## 実現性の見立て

| 要素 | 見込み | 方法 |
|---|---|---|
| 物理キーボード専用 IME | ◎ | `InputMethodService` で `onEvaluateInputViewShown()` を false にし、画面キーボードを出さない。キーは `onKeyDown`/`onKeyUp` で IME がすべて処理する |
| zenz による変換 | ◎ | azooKey フォークの llama.cpp（zenz のトークナイザ対応のため本家では読めない）を NDK でビルドし、JNI 経由で呼ぶ |
| ライブ変換 | ○ | 打鍵ごとに「かな→変換結果」を `setComposingText` で差し替える。zenz の小型モデルなら CPU で 1 打鍵数十〜100ms 台の見込み。前の推論の打ち切り、直前結果の再利用で遅延を抑える |
| 音声入力（押している間） | ○ | whisper.cpp。日本語は kotoba-whisper や large-v3-turbo の量子化版が候補 |
| 音声入力（逐次） | ○ | sherpa-onnx ＋ ReazonSpeech（ストリーミング zipformer）が候補 |
| 候補をカーソル近くに出す | △ | 最難関。標準の候補欄は画面下の帯。`CursorAnchorInfo` でカーソル位置は取れるが非対応アプリがある。オーバーレイ権限で浮かせる案もアプリ次第 |

## 既知の制約

- **DeX が先に取るキー**: Meta（Win）、Alt+Tab、Samsung の言語切替ショートカットなどは IME に届かない可能性がある。段階1で実機で洗い出し、表にして残す
- **未確定文字列の扱いがアプリで違う**: Termux などは composing text をうまく扱えない。アプリ（パッケージ名）別にライブ変換を切って直接入力にする設定を用意する
- **試験環境**: IME の基本動作はエミュレータや Pixel 3 で確かめる（本人の端末で試す前提にしない）。ただし DeX 固有のキー挙動と、zenz・Whisper の実速度は Galaxy 実機（Fold 7）でしか測れない。Fold 7 への導入は本人に頼むか、朝の確認一覧に積む
- **ビルド環境**: 作業機（Fedora）に Android SDK（`~/Android/Sdk`）と adb はある。java・gradle はまだ入っていない。重い NDK ビルドが足りなければ to-fu の WSL も使える（Kite で実績あり）

## 段階計画

### 段階0: 調査と方式決定

変換エンジンをどう載せるかを決める。候補は次の2つ。

- **A. azooKeyKanaKanjiConverter（Swift、MIT）を Swift の Android 向け SDK で動かす**。Zenzai・辞書・学習の仕組みをそのまま使える。ビルドの難度と apk サイズを確認する
- **B. 辞書とラティスは自前または Mozc（C++、BSD）、候補生成・評価に zenz**。Android でのビルドは楽

まず読むもの:

- [ニューラル言語モデル zenz を Android で使用する方法（Qiita）](https://qiita.com/Kazu_Project/items/536d89d1c499e1896b30)
- [StupidGame/Keynako](https://github.com/StupidGame/Keynako) — azooKey の Flutter 移植。Android の Zenzai を llama.cpp ＋ JNI で実装
- [azooKey の開発近況（2025年6月）](https://zenn.dev/azookey/articles/7a2c2d20a3cc4a)
- [nekomimist/skk-zenz](https://github.com/nekomimist/skk-zenz)、[unok/myime](https://github.com/unok/myime) — 他環境での zenz 組み込み例
- 既存の Android IME で zenz を組んだもの（KazumaProject 系など）があれば構成を確認する

決めたら、理由とともにこの文書へ追記する。

#### 段階0の決定（2026-10-02、CC が仮決定）

調査の詳細と出典は [RESEARCH-stage0.md](RESEARCH-stage0.md)。

**方式Bを採る。辞書とラティスは Kotlin で自前に持ち、zenz は llama.cpp（azooKey フォーク）を NDK でビルドして JNI で呼ぶ。**

| 部品 | 決定 |
|---|---|
| 辞書 | Mozc OSS 辞書（`src/data/dictionary_oss`）。ビルド時に自前の LOUDS 形式へ変換し、APK に同梱する。アプリ内のライセンス表示に IPAdic・ICOT の文面を入れる |
| ラティス・探索 | Kotlin で LOUDS トライ＋ビタビ（N-best）。UI なしで JVM の単体テストを回せる純 Kotlin モジュールにする |
| zenz | azooKey フォークの llama.cpp を submodule にし、CMake で arm64-v8a 向けに静的リンク。CPU 推論、4スレッド |
| モデル | zenz-v3.2-xsmall（Q5_K_M、21MB、Apache-2.0）に決定（2026-10-03、本人。small（74MB）は手元の評価で 92%→94% と差が小さく 3〜4 倍遅いだけなので、端末で選べるようにしていたのもやめた）。リポジトリには入れず取得手順を書く |
| zenz の使い方 | まず「辞書の N-best 上位を zenz で採点し、元の順位と混ぜる」と「貪欲生成の1候補を足す」。左文脈は `getTextBeforeCursor` で40文字。要求に番号を振り、古い推論は取り消す。発展形として Zenzai の制約付き再探索を Kotlin へ移植する |
| 参考実装 | Sumire（KazumaProject/JapaneseKeyboard、MIT）の LOUDS・ビタビ・`zenz_bridge.cpp`。依存はせず、必要な部分を読んで書くか、出典と MIT 表示を残して取り込む |

理由:

- **Kotlin で完結する**。方式Aは Swift ランタイムと Foundation（ICU 込み）だけで arm64 の .so が約86MB 増え、ツールチェーン（Swift 6.4 SDK、Fedora 向けは fedora41/ubi9 のみ）も1系統増える。エンジンは Sendable でなく、Kotlin の別スレッドから呼ぶと落ちる既知の問題もある
- **同じ構成が Sumire で実証済み**（MIT）。LOUDS・ビタビ・zenz の JNI・物理キーボードの設定まで揃っていて、読める参考がある
- **設計上の約束に合う**。変換ロジックを UI なしでテストでき、エンジン（ネイティブ）は zenz の推論だけに絞れる
- **Mozc 本体（`libmozc.so`）は採らない**。ビルドは可能だが JNI のクラス名が Google のパッケージに固定、protobuf の SessionHandler 丸ごとで、zenz をラティスに差し込むには C++ 改造が要る
- 辞書を Mozc にしたのは、IME 用のコストと接続行列が揃い、形式が素直なテキストだから。azooKey の辞書（Apache-2.0、語彙が新しい）は形式の一部が未文書なので、語彙を足したくなったら後で検討する

見直す条件: 変換品質が辞書＋zenz の並べ替えでは明らかに足りず、Zenzai の制約付き再探索の移植も重いと分かったとき。そのときは方式A（先例: ku6si0/azookey-android）を再検討する。

未確定のまま進めること:

- zenz-v3.2 の Apache-2.0 は HuggingFace のタグ表記でしか確認できていない。公開しないうちは問題にならないが、公開前に作者の表明を確かめる
- Android 実機での zenz の速度は未知。段階2で Fold 7 で測る

### 段階1: 最小の IME（Kotlin）

- ローマ字→かな、物理キー処理、画面 UI なし
- 日本語オン/オフ（JIS: 変換/無変換/かな、US: 設定で選んだキー）
- **DeX で届くキー・届かないキーの一覧**を実機で作る（エミュレータで先に骨組みを確認）

#### 段階1の実装と仮決定（2026-10-02）

- 構成: `core`（純 Kotlin。ローマ字→かな、未確定文字列、キー入力→IME の操作。JVM で単体テスト）と `app`（`InputMethodService`、物理キーの写像、設定とキー記録の画面）。`app` は `core` の `InputEngine` に入力を渡し、返ってきた操作（未確定の更新・確定・モード変更）を `InputConnection` に流すだけ
- 画面キーボードは出さない（`onEvaluateInputViewShown` が false）。日本語オンの表示はステータスアイコンだけ
- 日本語オン/オフ: JIS は変換・かな＝オン、無変換・英数＝オフ、半角/全角＝切り替え（常に有効）。US 用の右 Alt 単押し・Ctrl+Space・F13 は設定で個別に選べ、**既定は3つとも有効**（DeX で届かないものがあっても他で切り替えられるように）。右 Alt を切り替えに使う間は、右 Alt の押下自体をアプリへ渡さない
- 未確定がないときの Space・Enter・Backspace・矢印などはアプリへそのまま渡す。**Space は半角**のまま（全角スペースにしない）
- 未確定があるとき: Enter で確定、Esc で取り消し、Backspace で1文字（綴りの途中なら1字）消す、F6〜F10（または Ctrl+U/I/O/P/T。MS-IME と同じ割り当てで、本人の要望で 2026-10-02 に追加）でひらがな・カタカナ・半角カナ・全角英数・半角英数。未確定がないときの Ctrl+U などはアプリのショートカットとして通す。Space は段階3まで何もしない（変換キーの予約）。矢印・Ctrl 併用などは確定してからアプリへ渡す
- 日本語入力中の数字・記号・大文字は**既定で全角**（MS-IME・Google 日本語入力と同じ）。設定で半角にできる。`- , . [ ] / ~` は `ー 、 。 「 」 ・ 〜`
- キー記録: IME に届いたキーをアプリ内のファイル（最大 256KB）に書き、設定画面で読める。DeX のキー表（[DEX-KEYS.md](DEX-KEYS.md)）を adb なしで作るため、段階1では既定で記録する
- 本人が Fold 7 の DeX で使ってみて、ナビゲーションバーなども出ずに使え、不具合はなかった（2026-10-02）
- 確認: to-fu のエミュレータで、変換キー・F7・無変換・右 Alt・Ctrl+Space・F13・Backspace・Enter の動きと、画面キーボードが出ないこと（`mIsInputViewShown=false`）を確かめた。手順は [BUILD.md](BUILD.md)

### 段階2: 変換エンジン

- 段階0で決めた方式で、かな→漢字変換を動かす
- 端末上での 1 回あたりの推論時間を測り、記録する

#### 段階2の実装と結果（2026-10-02）

構成:

- `core/dict`: 辞書（kdic）と接続行列（kcon）の形式と読み書き。辞書は読みを辞書順に並べた配列で、共通接頭辞検索は1文字ずつ範囲を二分探索で絞る（計画では LOUDS としていたが、配列と二分探索で十分速く単純なので仮決定で変えた。サイズが問題になったら LOUDS にする）。表記が読みと同じ・読みのカタカナのときは文字を持たない
- `core/convert`: ラティス、前向きビタビ、後ろ向き A* の N-best（`KanaKanjiConverter`）。辞書にない文字は1文字の未知語（名詞,一般、コスト 12000）として置き、経路が切れないようにする。`Reranker` は言語モデルのインターフェース（`LanguageModel`）越しに辞書の上位を並べ替える。式は「対数確率 − ln(1+元の順位)」（skk-zenz と同じ）
- `zenz`（JVM モジュール）と `native/`: llama.cpp（azooKey フォーク、submodule）を静的に取り込んだ `libkanade_zenz.so` と、その Kotlin 側。候補の採点はプロンプトを系列 0 に置き、候補ごとの系列にプロンプトの KV を写して1回の decode でまとめて評価する。前回と共通するプロンプトの KV は使い回す。中断は abort callback
- `dictool`: Mozc の辞書の取得（コミット固定）、kdic への変換、評価。Gradle の `prepareKanadeAssets` がこれを呼んで、辞書・接続行列・モデル（リビジョンとハッシュ固定）を APK の assets（非圧縮）に入れる。取得物は `.cache/`（git 管理外）
- app: 辞書は APK から直接 mmap し、モデルは初回にアプリ内へ写す（llama.cpp がパスを要るため）。設定画面に「変換の試験」（1件の変換と、評価セットでの計測）を置いた。入力中の変換にはまだ使っていない（段階3）

評価（`eval/daily.tsv`、日常的な文 102 件、1位が許容解のどれかと一致する割合）:

| 方式 | 正解 | 備考 |
|---|---|---|
| 辞書だけ | 78（76.5%） | 「雨がフル」「機能帰国」「橋で食べる」など |
| 辞書の上位10件を zenz-v3.2-xsmall で並べ替え | 97（95.1%） | 改善 19、悪化 0 |
| 並べ替え＋zenz の生成1件 | 97（95.1%） | 生成を足しても1位は変わらなかった |

- Mozc の `evaluation.tsv`（609 件）は Mozc の挙動に合わせた回帰試験で、「この商品を解体」「ゴキブリを対峙した」のような変換を期待値に含む。言語モデルの良し悪しの判断には使わない（辞書だけで 88.8%、zenz で並べ替えると下がるが、下がった例の多くは zenz の方が自然）。zenz が実際に悪くするのは珍しい地名・固有名詞（田子浦→た強羅 など）で、小さいモデルの知識不足
- **Fold 7 の実測（2026-10-02、本人が設定画面の「評価セットで測る」で計測、4スレッド）**

  | 処理 | 中央値 | 95% |
  |---|---|---|
  | 辞書だけ（ラティス＋N-best 10件） | 3.6ms | 6.7ms |
  | zenz 生成 | 12.0ms | 18.8ms |
  | zenz 並べ替え 10件 | 27.6ms | 39.7ms |
  | 並べ替え＋生成 | 34.5ms | 54.8ms |

  正解は辞書だけ 78/102、並べ替え 96/102（手元の x86 では 97。浮動小数点の差と見る）。1件の変換では辞書 6.9ms、生成 21.6ms、並べ替え 32.7ms
- **段階3の方針（この実測で仮決定）**: 打鍵ごとに辞書の1位をすぐ出し（数ms）、zenz の並べ替えを裏で回して終わったら差し替える。打鍵の間隔（100〜150ms）より十分短いので待ち時間は置かない。次の打鍵が来たら古い推論は止める。生成は正解率が変わらず時間だけ増えるので、入力中は使わない
- 速度（参考）: 作業機は VM で CPU に AVX2 が見えず、llama.cpp が SIMD なしで動くので測定に使えない。エミュレータ（x86_64、最適化なし）では並べ替え 10 件が中央値 220ms、生成が 119ms。辞書だけは 3.6ms。**Fold 7 で設定画面の「評価セットで測る」を押して実測する**（arm64 版は dotprod と fp16 を有効にしてビルド）
- APK は約 90MB（辞書 37MB、接続行列 14MB、モデル 21MB、ネイティブ 2 ABI 分 10MB）。縮めるのは後回し（接続行列の疎な表現、辞書の圧縮、エミュレータ用 x86_64 を debug だけにする）

#### zenz のモデルの大きさの比較（2026-10-03 夜）

評価セットその2（`eval/daily2.tsv`、100 文。同音異義語・技術・会話・仕事の文）を足した。手元の x86（正解率だけ見る。時間は参考にならない）:

| | 辞書だけ | xsmall（21MB）で並べ替え | small（74MB）で並べ替え |
|---|---|---|---|
| その2（100 文） | 74% | 92% | 94% |

- どちらも悪くした文は 0。small は xsmall のおよそ 3.8 倍の時間がかかる（Fold 7 の xsmall が並べ替え 10 件で中央値 27.6ms なので、small は 100ms 前後の見込み）
- 仮決定: 既定は xsmall のまま。small に替えるかは Fold 7 で実測してから決める
- 並べ替えの式の β（辞書の順位をどれだけ残すか）を、2つのセット（202 文）で xsmall で比べた: β=0 で 191、0.5 で 188、1（いま）で 189、2 で 181。β=0 は少し多いが、辞書だけより悪くした文が 3 つ出る。差は小さいので β=1 のまま
- 採点する候補の数（topK）を 10→20・30 にしても正解は増えず（その2 では 1 減った）、時間は 2〜3 倍。10 のまま
- 並べ替えでも外れる文の多くは、正解が辞書の候補の 2〜4 位にある（「漢字/感じを覚える」「仕様/使用を確認」「店が開いて/空いて」など）。xsmall の判断の限界で、small や文脈（左の文）で変わりうる
- エミュレータ（最適化なしの x86_64）で small: 評価セット（102 文）の並べ替えが 98/102（96.1%）、中央値 801ms（xsmall は 220ms で 3.6 倍）。Fold 7 では 100ms 前後の見込み
- **左の文脈は効く**（`eval/context.tsv`、同じ読みで文脈により正解が変わる 30 文、`dictool eval-context`）: 辞書だけ 14、zenz 文脈なし 18、文脈あり 24（xsmall。直った 8・悪化 1）。small は 19→25。IME は入力の始まりにカーソルの前 40 文字を文脈として渡している
- **右の文脈も渡すようにした**（2026-10-03 夜）: zenz v3.2 は右の文脈（`\uEE07`）に対応している。入力の始まりにカーソルの後ろ 40 文字も取り、並べ替えのプロンプトに入れる（文の途中を直すとき効く）。`eval/context-right.tsv`（10 文）で文脈なし 5 → 右の文脈あり 9
- **コードのレビュー**（2026-10-03 夜、サブエージェントに読み取りだけで依頼）で見つかったものを直した:
  - 学習: zenz の並べ替えで1位が替わっただけの候補まで学習していた（並べ替えの結果が固まっていく）。利用者が候補を動かして1位以外を選んだときだけ学習する
  - 音声入力: 認識しているあいだに入力欄を替えると別の入力欄に入った／打ち始めた未確定を上書きした。入力欄ごとに番号を進めて古い結果を捨て、未確定があれば先に確定する
  - 自分の確定に対する遅れた選択範囲の通知で、次に打った文字をエンジンが忘れることがありえた。確定から 300ms のあいだは、未確定が消えた通知を見ない（仮の対処。起きたら期待する選択範囲と照らす作りにする）
  - パスワード欄ではキーに手を出さず記録もしない。シークレットモードなど学習しないよう求める入力欄では学習しない。端末アプリでは前のアプリの文を文脈に使わない
  - zenz のネイティブで、中断したとき KV と覚えている列が食い違った

- **操作**: 録音キー（既定 F12、設定画面で押して割り当て）を押している間だけ録音し（16kHz・モノラル、`VOICE_RECOGNITION`、最長 60 秒）、離すと認識して確定する。入力中の文字があれば先に確定する。カーソルの近くに録音中「🎤」、認識中「…」を出す。マイクの権限は設定画面で求める
- **幻聴の対策**: whisper は無音から「ご視聴ありがとうございました」を作りやすい（エミュレータの無音で実際に出た）。ほぼ無音なら認識しない、whisper が話していないと見た区間（no_speech_prob > 0.6）は捨てる、よく出る決まり文句だけなら捨てる
- **速さ**: エミュレータ（最適化なしの x86_64）で small が 8.8 秒の音声に 28.6 秒。Fold 7 は設定画面の「見本の音声で測る」で測ってもらう（zenz ではエミュレータの約8倍速かった）

- **whisper を速くした**（2026-10-03 夜）: whisper のエンコーダは既定で 30 秒の窓を丸ごと計算する。窓を音声の長さ（1 秒 50 フレーム＋余裕 64）まで縮めた（`audio_ctx`）。手元で 5 秒前後の音声が small で約 33 秒→約 8 秒（約 4 倍）。正しさは落ちず、6 文のうち 2 文はむしろ直った（30 秒の窓だと「火曜日→通りの」「喫茶店→寄りさ点」と誤った）。kotoba-whisper も約 4 倍速く、正しかった

#### 段階4の実装（第2弾、2026-10-03 夜、話しながら文字が出る）

- **方式の比較**（手元、to-fu の音声合成で作った6文、sherpa-onnx 1.13.8 の Python）
  - SenseVoice（int8、多言語）: 日本語が中国語の字になり使えない（「今日天気明日会议资料送宜」）
  - ReazonSpeech の zipformer（ja-en、int8、約 73MB）: 速く（遅い VM でも 5 秒の音声に約 0.2 秒）、ほぼ正しい。ただし句読点が付かず、前後に無音を足さないと文頭・文末を落とした（0.5 秒足して解消）
  - 日本語の本来の逐次（streaming）モデルは多言語の zipformer しか見つからなかった
- **決定（仮）**: 「疑似の逐次」。録音中 0.6 秒ごとに、ここまでの音声全体を ReazonSpeech で認識し、未確定文字列（Termux などでは帯）に出す。離したら whisper（取り込んであれば）で句読点の付いた文を作って確定する。whisper がなければ ReazonSpeech の結果、確定の文が作れなければ途中の文を使う
- **sherpa-onnx**: onnxruntime を静的に含む Android 用 AAR（v1.13.8、ハッシュ固定）を `.cache/` に取得して app の依存にする（`prepareKanadeAssets` が取得）。arm64 の .so が 24MB あるので、ネイティブを APK の中で圧縮するようにした（`useLegacyPackaging`、APK は 54MB）
- **ReazonSpeech のモデル**: HuggingFace の `csukuangfj/reazonspeech-k2-v2-ja-en` の int8 の4ファイル。whisper と同じく設定画面のボタンで4つまとめて落とす（ファイルから取り込むときは名前と大きさで見分ける）
- エミュレータ: 見本の音声（8.8 秒）で ReazonSpeech 0.58 秒（初回は読み込みで 4.5 秒）、whisper small 33 秒。どちらも正しい。マイクがないので、話しながらの表示は Fold 7 で確かめる


#### 聞き続けるモード・話して入れる句読点（2026-10-03、本人の要望）

- 録音キー・🎤 を 300ms より短く押すと聞き続けるモード。`VoiceEndpointer`（core、雑音の床を追い、その3倍か 0.01 を超える音が 150ms 続いたら話し始め、0.7 秒静かなら話し終わり、20 秒で区切る）で区切り、区切りごとに whisper（なければ ReazonSpeech）で文字にして入れる。話していない間の音は話し始め直前の 0.5 秒だけ残す。入力中の文字があれば確定まで待って入れる（`pendingVoice`）。途中の文字は未確定文字列ではなく帯に出す（打っている文字とぶつからないように）。もう一度押す・1分無言・入力欄の切り替えで終わる
- 短く押したかは、録音が始まってから数える（エミュレータでは録音の準備に 300ms 以上かかり、タップが長押し扱いになった）
- 話して入れる句読点（`SpokenPunctuation`、core）: くてん・とうてん・かいぎょう・はてなマーク・かぎかっこ など。漢字・ひらがな・カタカナの書き方を持ち、認識が付けた句読点との重なりをまとめる。「かっこいい」は除く。設定で切れる
- 入力中の文字だけを出す帯（音声の途中・Termux）は折り返して6行まで、幅は画面近く（900dp まで）に広げた
- エミュレータではマイクの音がないので、区切りは単体テストで確かめた。実際の声での区切りの具合は Fold 7 で見てもらう

## 設計上の約束

- IME の層（キー処理・表示）と、変換・音声認識のエンジン（ネイティブ）を分ける。エンジンは Kotlin のインターフェース越しに呼び、UI 側の都合をエンジンへ持ち込まない
- 変換ロジック（ローマ字→かな、文節操作、候補の選び方）は UI なしでテストできる形にする
- モデルファイルはリポジトリに入れない。取得手順を `docs/` に書く
